# Resident graph performance audit

Offline audit of `.work/frame-direct-kernels-20261030/resident-blocked-glue-full.json`, the current QDRX primary schedule, and the checked-in DSP source. No live device measurements were run for this audit. Times below are measured in the supplied report except where marked as a structural estimate.

## Concrete drains and bypasses

### Blocked HVX and dense staging

* **The existing software direct-HMX experiment is not the next quick win.** In `qd_graph.c:2115-2125`, it is gated by `dsp_direct_enabled`, u8, cached static weights, input/output blocked layouts, aligned origins and channel/output constraints. It feeds `dsp_direct_hmx_a` (`qd_direct_hmx.h:44-61`) instead of `t_read_region` plus dense input and packet packing (`qd_graph.c:2127-2137`, `qd_graph_dsp.c:166-210`). The supplied profile has this option off: 0/916 calls. Root reports an earlier 709-call software direct-gather A/B took about 1.8 s, with pack cost ~343 ms versus ~114 ms in the current path, so that implementation should not be blindly re-enabled. The newer native QNN 1x1 leaf is a different path and remains promising for its supported subset. The schedule census estimates **67,020,544 B** of dense activation materialization across 1,036 convolution commands if all took the dense path; this is local VTCM work under native pool1 and is deliberately not counted as DDR traffic.
* **Non-convolution blocked kernels remain material.** `k_input_slice_pad` (`qd_graph.c:481-505`) fills a full dense scratch tensor, copies the valid input window, then calls `t_write`; specialize it to write valid spans and padding directly into blocked output. `k_im2col` (`523-547`) does scalar per-channel copies for u8 and then repacks; vectorize contiguous channel spans or fuse the gather into HMX-A preparation. `k_space_to_depth` (`550-577`) builds a dense regional input and output before the blocked write; add a blocked HVX gather/store implementation. These are correctness-preserving kernel replacements, not merely a faster memcpy. The existing profile gives 47.4 ms input slice/pad, 51.3 ms CH/FH im2col and 44.1 ms space-to-depth-family time.
* **Hot non-convolution numeric work also deserves direct implementations.** `k_sign` (`qd_graph.c:1164-1207`) has 49.6 ms on only 12 CH calls; `k_transpose` (`941-970`) has 47.8 ms across 111 calls and scalar element gathers; `k_add_u8` (`643-663`) has 37.5 ms across 170 calls in CB. The blocked glue already reduces u16 sign and linearclip to HVX paths (`qd_graph.c:795-874`, `1164-1198`), but only linearclip counters are reported here; the remaining profile cost makes per-kernel exact output and timing A/Bs useful. `dsp_block_u8/u16` in `qd_glue_hvx.h:41-112` transfers one fragment at a time with substantial scalar index work. A next HVX experiment is to hoist block-table/address calculations and issue multiple independent fragments before stores; do not change padding, alias or block-boundary behavior.

### VTCM binding and liveness

The primary QDRX pool1 is exactly 8 MiB. Schedule census counts **11,249,796 B** of required pool1 boundary traffic: op4 weights-to-pool1 7,833,732 B; op26 spill/fill 3,407,872 B; op17 activation copies 8,192 B. At the measured ~10 GB/s bulk envelope this is a **1.125 ms optimistic floor**, not a full-graph projection. Including input/output host transfers yields 12,888,324 B or 1.289 ms. Even ideal DDR/VTCM movement alone cannot account for the remaining ~1.1 s, and deleting that traffic cannot approach 20 ms without replacing major compute/layout paths.

Whole-pool1 VTCM binding is not a small allocator toggle. `qd_graph_dsp.c:20-40` implements a 512 KiB block cache at `0x31250000`, inside the same 8 MiB VTCM range; `qd_graph_dsp.c:169-210` uses fixed HMX packing/staging at `0x31000000` and assumes up to `0x2d0000` bytes there. If pool1 is directly mapped at `0x31000000`, those stores/cache lines can overwrite live graph tensors. Native binding needs a VTCM-aware tensor access path (bypass block-cache copies when storage is already in VTCM) and an explicit scratch allocator/lifetime rule.

Reproduce the pool liveness coverage with `python3 frame/perf_audit/vtcm_liveness.py [image.qdrx]`. For the exact primary image SHA shown in `frame/vtcm_lease/CENSUS.md`, this finds a stable **512 KiB never-referenced tail range** at pool1 offsets 7.5–8 MiB, and at least 512 KiB largest contiguous free at every HMX command. A current-layout estimate (build has no `QDC_NATIVE_BUILD`) places packed-HMX workspaces at about 106 KiB–3.02 MiB and fits the largest conservative live-free run for **328 of 1,036** convolution commands. The other commands need a larger contiguous range; some of the estimated workspaces exceed the current 2.95 MiB VTCM bound and should be treated as non-HMX fallback cases. This supports an incremental native path for 512 KiB-class work (including the recent direct 1x1 probe) and a subset of small packed convs, provided scratch is relocated into an interval proven free for the entire async HMX lifetime. It does **not** support moving the existing 2.5–2.8 MiB fixed fallback scratch wholesale into the schedule. The interval estimate is a planning signal, not a proof: it does not model internal alias/view semantics, worker lifetime after submission, or hidden accesses beyond QDRX input/output references. Before using a dead range, generate command-level live block maps from the exact image and assert it against all tensor blocks, op4 destinations and `fv` spans.

Thus a phased route is feasible: first route eligible direct 1x1 work into the stable 512 KiB tail, then try small packed HMX layouts with per-command dead-range allocation; larger layouts need tiled native kernels or schedule/lifetime changes. Full native VTCM needs reworking the fixed block cache and HMX workspace together, not activating old HMX staging beside the graph pool. The old HMX staging path and an 8 MiB native graph tensor pool cannot coexist at overlapping VTCM addresses.

### Scalar/cache policy versus bulk-copy issue spacing

`qd_graph_dsp.c:132-145` has two materially different `memcpy` paths. If either endpoint falls in QDO's cached scalar ranges (pages 0, 2 or 3), it skips HVX and copies scalar words; otherwise it issues one HVX load then one store per 128-byte loop iteration. Mutable pools are allocated in offsets 16–32 MiB by `resident_dsp.py:57-72`, mapping to uncached page1 `0xa1000000..0xa2000000`, so pool1/spill current transfers should use the vector branch. The custom loop is still dependency-spaced (each store follows its load); for confirmed uncached, non-overlapping bulk copies, test eight independent HVX loads followed by eight stores. Keep cached endpoints on the scalar/cache-maintained path.

The supplied report has no direct-affine test. Root separately reports an approximately 7 ms direct-affine operation on only several MB, about 1 GB/s versus the ~10 GB/s bulk envelope. That points to per-operation dependency/fragmentation/cache policy, not a raw DDR ceiling. Minimal A/B: same range/bytes and clocks, (1) one aligned uncached bulk copy, (2) current `memcpy`, (3) 8-load-unrolled copy; separately repeat with a cacheable source/destination and required `dccleaninva`. Record bytes, address class, alignment, whether source/destination overlap, and exact result hash. Do not add a fast path to cached memory based only on pointer ranges.

For pool1 spill/fill, the linked `memmove` in the available DSP disassembly dispatches into `rmemcpy_asm`, whose bulk loop uses paired 64-bit scalar `memd` loads/stores; the current custom `memcpy` has a 128-byte HVX load/store path. Exact primary schedule census: 26 spill commands / 144 spans / 1,703,936 B and 62 fill commands / 85 spans / same bytes; every pool1 address and length is 128-byte aligned, spans are 2–65,536 B, highest end is below 8 MiB, and pool1/spill are separate configured pools. Root's opt-in `QDS_FAST_SPILL=1` switches these proven disjoint uncached spans to existing `memcpy`. Hardware result: primary fill+spill attribution fell **93.5 ms → 0.788 ms**, alternate **71.7 ms → 0.618 ms**; the full 54-case + 2-warm matrix is now exact, with warm medians **964.86 ms primary / 954.77 ms alternate** versus prior **1,055.91 / 1,031.33 ms**. The full-pool-prefix random checks passed for both models. This establishes the quick win; 8-way vector issue is not the next step. The old profile's remaining 195.9 ms group included sign, so do not treat it as the current measured remainder after sign's separate ~1.2 ms optimization. Pool6 is a pool-specific spill area, so keep the generic semantics for any other mapping.

The inspected file is `frame/build/qd_graph_dsp.dis` (SHA-256 `dec3c818c72d922c60b75c5f4d116bd52b073db9f62583a71d58a152cfb153eb`; filesystem timestamp 2026-10-30 01:46); it predates the current `qd_graph_dsp.elf` timestamp (14:08), whose SHA-256 is `5fa45a82f4c6a905e621db56f2432225aa4baf4057fd26faa792c10d10e62e2e`. Treat the disassembly's libc `memmove` implementation as indicative only, not as proof of the exact code linked into the latest engine. Regenerate disassembly from the exact `QDS_FAST_SPILL=1` artifact before concluding.

### Scalar metadata and schedule/DMA

The nested `metadata_ms=17.30` is about 1.6% of wall. `dsp_command_begin` / `dsp_tensor` in `qd_graph_dsp.c:75-90` copy metadata into L2 and serially look up tensors; an indexed command-local metadata table is a possible exact optimization, but it cannot close the gap to 20 ms. Warm allocator time is zero; cold allocator cost is not the recurring bottleneck. Weight packing/misses total about 15.2 ms warm.

The graph has asynchronous HMX and a conservative hazard-based conv hoister (`qd_graph.c:2437-2455`, enabled by default at `2618`); `qdg_run` drains when footprint hazards require it (`2476-2507`). The high HMX command count does not mean all compute is serial, but this profile provides no separate overlap/idle counter, so a scheduling gain cannot be inferred. QDRX `@DmaCheckpointSet`/`Wait` map to `k_nop` (`resident_schema.py`); current op4 copies are synchronous `memmove` (`qd_graph.c:511-519`), op17 activation copies are explicit graph copies, and op26 is synchronous `memmove` per `fv` span (`1108-1122`). There is no graph DMA queue in these handlers. Near-term scheduling work should preserve the existing hazard footprints while batching pool1 transfers and measuring HMX wait/drain time separately. A real DMA pipeline requires an async descriptor queue, explicit source/destination lifetime retention, and dependencies that allow overlap; it is a required native/runtime change, not an option bit.

## Smallest useful experiments and 20 ms gates

1. The fast-spill A/B is complete and validated at full case coverage; keep it opt-in pending integration but do not spend another cycle on the same copy body.
2. Integrate/profile the distinct native QNN 1x1 adapter in the 512 KiB tail, with output hashes and VTCM lease fingerprints. Root reports the adapter works alongside the original spatial expert; compare end-to-end timing before generalizing to other convs.
3. Prototype pool1-native tensor access with the block-cache bypass first, keeping old HMX scratch disabled. Use only the static 512 KiB tail for the first native leaf; the VTCM byte snapshot remains preserved around the whole exclusive session.
4. For larger packed-conv workspaces, add a command-live-range allocator and scheduler resource hazards. `qdg_run` can keep an HMX request inflight while executing independent graph ops (`qd_graph.c:2492-2505`), so a scratch hole that is free at submit may become a future tensor write before the worker finishes. Reserve its blocks until completion or drain before an intersecting command; the current tensor footprint check does not include scratch.
5. After the native mapping/allocator safety model is proven, replace the remaining large non-conv scalar kernels (transpose, pad/slice, add) with blocked HVX kernels and validate byte-exact graph outputs. Root separately reports the sign path has fallen from about 49.6 ms to about 1.2 ms on hardware; include that exact build in the next full profile before accounting the gain against the remaining budget.

The schedule's ideal boundary-copy floor is already just 1.125 ms (1.289 ms with graph I/O), leaving about 18.9 ms of a 20 ms budget before compute, command latency, HMX contention, DMA setup, eye-client contention, cache maintenance and imperfect overlap. This says data movement volume alone is not a 20 ms barrier; it is **not** a 20 ms performance prediction. The current ~1.1 s budget has hundreds of milliseconds in convolution and ~300 ms in non-convolution, copy, and layout rows. A 20 ms target requires measured multi-kernel replacement and scheduling gains, not VTCM binding alone.

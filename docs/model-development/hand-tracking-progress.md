## Why it was slow, and what changed

The matrix unit was never the bottleneck: a direct tile costs about 18 cycles. **A hardware thread issues one packet per three cycles** (simulator `Pcycles/Packets` is 3.0, and silicon depthwise cost matched that), so packet count is the cost of HVX work. Simulator packet counts are a useful guide, though they do not model memory time.

- **Planar layout.** Activations are `[32-channel block][pixel pair][32 channels][2 pixels]`, in whole 32-pixel tiles, with rows padded to an even physical width and a pad column kept zero. External I/O remains FP32. The FP16 plan is computed at session open and lives in L2.
- **In-place HMX.** All pointwise convolutions use `hx_hmx_strip`: no packing, one completion per op. Every deep load is one tile-aligned tile, so none can cross the 4 MB VTCM TLB page boundary; no TLB remap is used.
- **Resident records.** HMX weights, depthwise filters, bias tables and PReLU slopes stay in VTCM between runs of a graph. Switching graphs or running FP32 re-stages them.
- **Depthwise.** `fp16_depthwise.S` is generated by `gen_depthwise.py`: two packets per tap, with 3×3 weights held in registers and row setup overlapping the previous pair's conversion and clamp. A 3×3 pair takes 22–25 packets and a 5×5 58–63. The C `dw_border` remains for the ReLU[-1,1] clamp and windows that do not fit, and produces identical bits.
- **Channel compaction.** `hexecutor/offline/compact_hxfg.py` removes channels that are exactly zero or never read. MediaPipe's landmark model carries up to 742 of 1152 dead channels per layer; 4,976 are removed in total, weights drop from 5.45 to 3.88 MB and all stay resident. It then orders internal channels by descending weight magnitude, which took gradient handedness from 0.0205 to 0.0191. `prepare_mediapipe.py` applies it. Palm has no dead channels, and its measured errors did not change.
- **Four workers.** Physical hthreads 0, 1, 2 and 5. HT5's stack had to move from DDR to L2 for tensor sessions: on DDR, landmark took 5.04 ms with four workers against 1.51 ms with three; on L2 it took 1.23 ms. The host refuses an engine and bootstrap that do not both use four workers.
- **Even partitioning.** Depthwise work is split by (block, row) units. Whole-block splits left one thread with two of five blocks and every other waiting.
- **Padded windows.** Depthwise copies each thread's rows into a zero-padded window, so nearly every pair runs the scheduled loop. The compact RGB image is similarly zero-padded, which removed its scalar border path: pack fell from 475k to 142k cycles on three workers.
- **Serial DDR import.** One thread reads the input from DDR, then all workers convert in VTCM. Three threads reading concurrently were slower than one.
- **Parallel jobs.** RGB conversion and packing, activation clamps, non-resident weight copies and output export run on all workers.
- **Host completion.** `sleep_for(200 µs)` polling saw results late. The host now sleeps through most of the previous DSP-timer duration, then spins briefly. It must use the DSP timer: a host-observed duration includes the sleep, and an early version locked itself at 23 ms.
- **Cancellation checks** read uncached DDR, so they run every eighth operator rather than before each.
- **Palm transforms.** Fast paths for 2×2 max pool, trailing-channel pad and width concat; reshape copies runs without per-pixel division.
- **Native rounding.** ADD and resize use native QF32→HF instead of exact RNE. Errors were unchanged to six digits on the simulator cases checked and all nine cases pass on Frame. External import stays exact RNE.

## Rejected, with evidence

| Idea | Result |
| --- | --- |
| FP32 residual state (the earlier mixed candidate) | Frame: 9.41 ms vs 6.13 ms for 0.0005 of error. Removed. |
| QF16 depthwise accumulation | Simulator: real-image handedness 0.0003 → 0.0082, palm score error 0.14 → 0.95. Removed. |
| HVX IEEE float instructions (`.sf += vmpy`) | Unavailable on the Frame. The separate FrameNPU project ran them on device (2026-11-16, same CDSP firmware `4f9fd567…`): IEEE FP32 multiply/add, FP16→FP32 multiply-accumulate and FP16 accumulation all write zeros. Nothing faults or hangs, and QFloat in the same job is correct. `libQnnHtpV75Skel.so` contains none of these instructions either. Use qf16/qf32 only. See [kernels](../hexecutor/kernels.md#unavailable-hvx-ieee-float). |
| HMX depthwise | Estimated only about 25% better than scheduled HVX at the time, with changed numerics and more risk. Not built. |

| Resize (2) | 300,933 | 7% |
| ADD (30) | 250,890 | 6% |

The cancellation change later took landmark `other` to about 160k cycles.

Next, in expected value order:

1. **Host-side FP32→FP16 conversion** would halve the input DDR read and remove DSP conversion. The host must then know the DSP selected the FP16 path.
2. **Depthwise scaling.** A 5×5 is near its two-packets-per-tap limit, so gains must come from better parallel scaling or fewer taps.
3. **Palm reshape** is still a scalar copy, and matters less because detection is infrequent.

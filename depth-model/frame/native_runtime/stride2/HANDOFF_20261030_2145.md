their fixture-oracle comparisons are diagnostics only; they are not evidence
that the QDRX V73 schedule is supported.

  `r3:2 = combine(r18,r17)` and `r5:4 = combine(r16,r21)`. These are callee

- The hook records six leaf arguments, eight request words, six descriptor
  words, and sixteen config words. The assembly source compiles with the SDK
  container toolchain using `-c`.

## Remaining blocker

`v73_capture/qnn_v73_capture_harness.c` is still a copied V69 harness and must
not be treated as a V73 driver. No V73 capture or numerical run was performed.
The executable harness still needs a driver that constructs the actual V73
worker input objects and invokes the correct entry ABI. In particular, the
V75 helper makes indirect type callbacks through the tensor object's vtable,
uses a shape-derived HMX configuration, and has runtime dependencies (division,
logging/string/math helpers and alternate leaf paths). The current assembly
contains provisional stubs for a few non-HMX runtime calls; they have not been
validated. The capture stub records data and returns; it does not invoke the
V73 leaf.

and QDRX sequence-224 tensor roles. Build a fresh C driver (replace the copied

fixture. Only after that does it make sense to replace the hook with a call to
the extracted V73 leaf and check the full output against the independent
oracle. Keep capture and numerical results labeled separately.

The generated V75 `.S` uses absolute `.org` placement. Link/run it only with a
layout that preserves these original VA offsets (and maps the extracted
provider call targets); an ordinary relocatable placement is not equivalent.
